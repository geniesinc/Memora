# Memora — Benchmark Data Generation

This directory contains the pipeline used to generate the Memora benchmark
released under [`data/`](../data). It transforms persona + memory-category
metadata into:

1. **Sessions** — discrete user/agent events with explicit memory operations
   (add / update / delete) and snapshots of memory state after each session.
2. **Conversations** — natural multi-turn dialogues grounded in each session's
   memory operation, generated by an LLM following intent-based flows.
3. **Evaluation questions** — remembering / reasoning / recommending questions
   derived from the memory trail, each tagged with `memory_evidence` and
   `forgetting_evidence` for FAMA scoring.
4. **Quality validation** — automated checks for memory-state consistency and
   question-evidence integrity (optional but recommended).

```
metadata + persona
        │
        ▼
┌──────────────────────┐
│ session_simulator.py │  Stage 1 — sessions + memory states
└──────────────────────┘
        │
        ▼
┌──────────────────────────────────────┐
│ conversation_generation/             │  Stage 2 — conversations
│   memory_grounded_generator.py       │  (LLM, intent-based flows)
└──────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────┐
│ question_generation/                 │  Stage 3 — eval questions
│   unified_question_generator.py      │
└──────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────┐
│ quality_checks/                      │  Stage 4 — validation (optional)
└──────────────────────────────────────┘
```

The released benchmark in `data/{weekly,monthly,quarterly}/<persona>/` was
produced by running this pipeline once per timeline × persona combination.

## Setup

```bash
# From the data_generation/ directory:
pip install -r requirements.txt

cp .env.example .env
# Edit .env and set OPEN_ROUTER_API_KEY (used by the conversation generator
# and the LLM-based quality evaluator). Only Stage 2 + the LLM evaluator
# require this; Stages 1, 3 and the deterministic validators do not.
```

Python 3.10+ is recommended.

## Quick start — reproduce one persona

The example below regenerates a *weekly* dataset for the
`software_engineer` persona end-to-end.

```bash
cd data_generation

# Stage 1: simulate sessions + memory state evolution
python session_simulator.py \
    --config meta_data/memory_configs/memory_config_weekly.json \
    --persona software_engineer \
    --start-date 2025-06-01 \
    --end-date 2025-06-07
# -> output/sessions_<timestamp>_software_engineer/
#      ├── new_sessions.json
#      ├── memory_states_by_session.json
#      └── memory_evolution_summary.json

# Stage 2: generate conversations for each session
cd conversation_generation
python memory_grounded_generator.py \
    --session-file ../output/sessions_<timestamp>_software_engineer/new_sessions.json \
    --generate-all
# -> output/sessions_<timestamp>_software_engineer/conversations/
#      ├── successful/session_NNNN_<memory_type>.json
#      └── generation_report.json
cd ..

# Stage 3: generate evaluation questions
python question_generation/unified_question_generator.py \
    --session_directory output/sessions_<timestamp>_software_engineer \
    --timeline weekly
# -> output/sessions_<timestamp>_software_engineer/
#      ├── unified_questions_weekly_<timestamp>.json
#      └── evaluation_questions_software_engineer.json
```

### All personas in one go

```bash
# Stage 1 for all 10 personas
./run_session_simulator.sh weekly 2025-06-01 2025-06-07

# Stage 2 for any persona output folder that doesn't have conversations yet
./conversation_generation/run_conv_gen.sh

# Stage 3 over every session folder
./question_generation/run_question_generation.sh weekly
```

Swap `weekly` for `monthly` or `quarterly` to regenerate the longer-horizon
variants of the benchmark.

## Outputs

Each Stage-1 run creates a unique `output/sessions_<timestamp>_<persona>/`
directory. Subsequent stages write into the same directory so the full
generated record for one persona stays self-contained:

```
output/sessions_<ts>_<persona>/
├── new_sessions.json                  # Stage 1: session list
├── memory_states_by_session.json      # Stage 1: post-session memory states
├── memory_evolution_summary.json      # Stage 1: stats
├── conversations/                     # Stage 2
│   ├── successful/session_NNNN_<memory_type>.json
│   └── generation_report.json
├── unified_questions_<timeline>_<ts>.json   # Stage 3 raw
└── evaluation_questions_<persona>.json      # Stage 3 final, used by the benchmark
```

The `evaluation_questions_<persona>.json` file is the artifact released under
`data/<timeline>/<persona>/` in the public dataset.

## Memory model

| Memory type        | Categories                                            | Operations                  |
| ------------------ | ----------------------------------------------------- | --------------------------- |
| `preference_memory`| movies, books, music, travel                          | add / update / delete       |
| `activity_memory`  | food_expenses, step_tracker, todo_list, calendar      | add (most), update for some |
| `content_memory`   | project_proposal, email, social_media, meeting_notes  | add / update / delete       |
| `goal_memory`      | food_budget, fitness                                  | set / update                |
| `no_memory`        | general conversation, no memory operation             | —                           |

Behaviour for each category (frequency, allowed operations, weights,
completion thresholds) is declared in
`meta_data/memory_configs/memory_config_<timeline>.json`. The simulator is
fully driven by these configs — adding a new memory category requires only
metadata, not code changes.

The 10 personas (`academic_researcher`, `business_executive`,
`content_writer`, `creative_designer`, `financial_analyst`,
`management_consultant`, `marketing_manager`, `sales_manager`,
`software_engineer`, `startup_founder`) are defined in
`meta_data/persona_traits.json` and provide preferences and content samples
for the corresponding metadata files.

## Quality validation (optional)

After generation, run:

```bash
# 1. Verify each session's declared operation matches the memory-state diff
python quality_checks/memory_state_validator.py \
    output/sessions_<ts>_<persona>

# 2. Validate that every generated question has resolvable
#    memory_evidence / forgetting_evidence in the conversation history
python quality_checks/validate_question_generation_pipeline.py \
    --session-dir output/sessions_<ts>_<persona>

# 3. Aggregate metrics across all personas
python quality_checks/calculate_question_metrics.py --output-dir output
```

See `quality_checks/README.md` for the full checklist.

## Cost notes

Stage 2 is the only LLM-heavy stage. With `google/gemini-2.5-flash` the
average session costs roughly **$0.001–0.002** (~12k tokens per session).
A full weekly run (10 personas × ~150 sessions ≈ 1,500 sessions) lands in
the **$2–3** range. Quarterly runs (~2,000 sessions / persona) are roughly
13× larger. Stages 1 and 3 are deterministic and have no LLM cost.

## Reproducibility

The simulator uses Python's `random` module without an explicit seed by
default. To produce reproducible session lists, set a seed at the top of
`session_simulator.py` (`random.seed(...)`) before running, and pin the
LLM model + temperature for Stage 2 inside
`conversation_generation/prompt_manager.py`. The released benchmark uses
`google/gemini-2.5-flash` with default temperature.
